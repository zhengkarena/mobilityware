02 · The Data Spine

Unified attribution architecture

Building the trustworthy backbone before building any chart on top of it.

AThe problem, stated plainly

Eight silos, four install counts, one decision to make

UA data at any modern studio lives in eight-plus silos. Ten ad networks each report their own installs, spend, and self-attributed conversions. An MMP — AppsFlyer, in our case — tries to unify them, but carries its own attribution windows and fingerprinting limits. SKAN postbacks arrive twenty-four to seventy-two hours late, aggregated and privacy-preserved by design. The Play Install Referrer is deterministic on Android but limited in fields. Store consoles own ground-truth revenue but not user-level acquisition data. The internal warehouse holds in-app events, retention, and IAP — but joining it to UA data depends on a single install ID matching cleanly across systems. Ad-mediation platforms (AppLovin MAX, ironSource LevelPlay) report the ad-revenue events that actually drive ROAS in an ad-monetized portfolio like ours, and they arrive on a different cadence still.

Each source has its own definition of an install. They disagree, often by double digits. The result is a UA Manager who can open four dashboards on the same channel and see four different "true" install counts — and a chain from ad impression → click → install → in-app behavior → LTV that is broken at multiple seams. Attribution becomes guesswork. Budget allocation becomes politics. Incrementality becomes the only honest answer to "did this campaign actually cause anything?"

You can't optimize what you can't trust. The first deliverable any UA analyst should ship is the spine that makes the rest of the work honest.

Two reads from this table set up everything that follows. One: there is no single source that is both complete and trustworthy — every input has a known seam. Two: the seams are predictable, which means they can be reconciled by rule rather than re-litigated weekly. That rule-set is Section D. The architecture that holds the rule-set is Section C.

EThe trust-score framework

Five dimensions, ten networks, one weekly scorecard

The composite trust scores in Section B aren't editorial — they roll up from five measurable dimensions, scored weekly per network. Every dimension is something we can compute from data we already have. The dot rating below is the same instrument used in the sources table; a score of here means the same thing it means there.

MMP-to-Network reconciliation

Three reads. Apple Search Ads sits at the top because Apple owns the deterministic chain end-to-end — it is the cleanest paid channel we have, and the channel mix should reflect that. Meta sits at the bottom not because it doesn't drive installs, but because the data we get back from it is the least trustworthy: heavy AEM aggregation, no creative-level visibility on iOS post-ATT, and a self-attribution bias confirmed by geo-holdout (Tab 6). Spending on Meta is fine; trusting Meta's reported ROAS without a discount factor is not. Moloco normally scores 4 / 5 — today it carries an inline note because the reconciliation in Section D caught a probabilistic-share regression. The framework didn't cause the alert; the framework is what makes the alert legible.

D2 — the SKAN-to-probabilistic ratio — is the one to watch hardest. A partner that delivers a lot of probabilistic installs but thin SKAN signal is, mechanically, a partner whose attribution we cannot independently verify. That is the dimension that should set the ceiling on incremental budget allocation.

FThe SQL view

One query, one fact row, ninety days of history

Below is the canonical query that builds fact_ua_daily — the table that everything downstream reads from. It pulls from the five sources we've been talking about (network spend, MMP, SKAN postbacks, ad-revenue events, IAP events), reconciles them on the join keys we trust, and applies the trust-weighted blend from Section E. This is the query I'd want to land on first because every other SQL artifact in the spine is a rollup of this row shape.

fact_ua_daily.sql BigQuery

The design tradeoff worth naming: the blend joins on install_id where MMP gives us one and falls back to SKAN-postback aggregates only when MMP runs materially below SKAN on iOS rows. That's deliberate — joining SKAN aggregates to user-level rows is impossible without inventing identity, and inventing identity is how double-counting starts. We accept aggregation loss on the SKAN-only top-up in exchange for never inflating an install that already exists at user-level. The trust-score weight on the top-up is what keeps a low-confidence partner from puffing up the blended count beyond what their measurement actually supports.

GIdentity stitching, honestly

The chain works in three regimes — and one of them isn't really a chain

Android. The Play Install Referrer carries a deterministic click ID and timestamp from the click that earned the install; the GAID on the device gives us a stable user identifier (until reset). The MMP consumes the referrer and writes a single install_id that ties through to in-app events, ad-revenue events, and IAP. Ad impression → click → install → in-app behavior → LTV is one row, joined cleanly. Roughly 55% of our portfolio installs sit in this regime, and they're the cohort our retention and pLTV models can be most confident about.

iOS, opted-in. When a user grants ATT consent, IDFA is available and the chain looks the same as Android — deterministic, user-level, joinable end-to-end. The catch is the consent rate: in casual card games we see roughly 25–35% opt-in, with material variance by geo and creative. So this is the highest-quality iOS data we get, but only on a quarter of the iOS cohort. We treat this slice as gold for modeling but never pretend it represents the whole iOS population — opted-in users self-select, often toward higher engagement, and projecting their behavior onto the opted-out cohort overstates LTV in predictable directions.

iOS, opted-out. SKAN. Conversion-value mapped, aggregated at the campaign × CV bucket level, delayed 24–72 hours, with no individual user identity by design. There is no clean stitch from a single ad impression to a single user's in-app behavior in this regime, and probabilistic fingerprinting — what's left of it — is shrinking under Apple's policy enforcement. The honest framing: we have aggregate signal, not a chain. Section F's blend handles this by topping up MMP with SKAN aggregates where MMP runs thin, but the top-up is a population estimate with a trust weight, not a row-level join. Anyone who tells you they have a clean per-user attribution chain on opted-out iOS is selling something.

HWhy incrementality is the honest backstop

The cleanest stitched spine still tells you correlation, not causation

Even with every join in Section F running clean, there is a question the spine cannot answer on its own: did this campaign cause this install, or would the install have happened anyway? Last-click attribution credits the platform that closed the conversion. That credit is correct accounting and incorrect causation. A user who would have organically searched Solitaire today gets credited to the Meta retargeting ad they happened to see this morning. Multiply that across every channel and the reported ROAS the spine emits is systematically too generous, in ways that vary by partner.

The dashed amber arrow in Fig. 1 is where this gets fixed. Holdout-based incrementality tests — geo holdouts, ghost-bidding, PSA tests — measure causation directly by comparing a treated population to an untreated control. The number that comes out of an honest holdout is an incremental rate: the share of attributed conversions that wouldn't have happened without the campaign. That number writes back into the trust-score weighting in Layer 2, which is what makes the loop a loop. Tab 6 walks through two of these end-to-end — a bid-strategy test on Google UAC and a geo-holdout on Meta — and the Meta result is the one that produces the discount factor the spine then applies to every Meta-attributed row going forward.

IWhat I'd ship in my first 30 days

Five concrete artifacts that turn the spine from a slide into a system

Each of the five below is a thing that exists, runs on a schedule, has an owner, and a Slack channel that gets pinged when it breaks. None of them are aspirational.

  1. Daily reconciliation report
    The Section F view runs nightly via Cloud Composer; output lands in #ua-data on Slack at 8:00 a.m. PT every weekday. Channel × OS × game rows with anchored install counts, network gaps, SKAN gaps, and any composition-shift flags from the prior day. The Moloco-style flag in Section D is one row in this report.
  2. Per-network trust-score scorecard
    Refreshed every Sunday at 9:00 p.m. PT against the prior 7 days. Reads from mw-ua.ref.network_trust_scores; the Section E grid is the human-readable face of this table. Alerts the channel owner if any of D1–D5 drops by one dot week-over-week, with the contributing rows pre-attached.
  3. SKAN postback completeness alert
    Real-time monitor on the skan_cv_received / skan_postbacks_total ratio per (channel × app × os). Fires a Slack ping when the ratio drops below 70% completeness for two consecutive days. Alert payload includes the partner AM email pre-filled and the trailing-14-day completeness trend, so the responder has the conversation half-written before they open the ticket.
  4. Creative-ID propagation audit
    One-time deep dive across all ten networks documenting which carry creative_id cleanly, which only on certain ad formats, and which not at all. Output is a maintained sheet plus a weekly automated check that flags new creative IDs appearing in spend without matching installs — that's how the Tab 4 creative analysis stops going dark on specific channels without anyone noticing.
  5. Data dictionary for fact_ua
    Every column documented: source CTE, source table, transformation logic, owner, freshness SLA. Lives as git-versioned markdown in the analytics repo, not a Notion page that decays. Anyone on UA, Creative, or Finance can answer "what does this column mean and when was it last refreshed" without pinging the data team. This is the artifact that compounds — every new analyst onboarded to the team starts here instead of in a 1:1 with someone senior.
